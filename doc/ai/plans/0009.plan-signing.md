# 0009. Подпись RPM и исполняемых файлов своими ключами (статус: запланирован, 2026.11.21)

Цель: подписывать наши RPM и бинарники так, чтобы они **запускались при
`ima_appraise=enforce`** — без отключения IMA на загрузке. Плюс — понять
механику доверия (OMP CA, `.ima` keyring, rpm-validation plugin) и, если
возможно, получить developer-сертификат официально.

## Что уже известно (REPORT §7, проверено экспериментально)

* IMA appraisal проверяет xattr `security.ima` (ima-ng хеш/подпись) у каждого
  исполняемого файла и `.so` (MMAP).
* `security.ima` **с подписью** принимается только если ключ есть в `.ima`
  keyring; туда попадают только сертификаты, подписанные доверенным (OMP)
  ключом. Наш самоподписанный ключ `747cac19` → `Could not load certificate`.
* Загрузчик сертификатов: `/usr/libexec/ima/load-certificates`
  (`ima-certificates-loader.service`), источник — `/var/lib/rpmsign-external/db.sqlite`.
* Хеш-аппрайз (`security.ima` = хеш, без подписи) без ключа — не проверялся;
  ключевой эксперимент.
* `rpm-validation`: CMS-подпись «developer», цепочка к
  `/etc/keys/packages/ca.pem`, keyid == `system-developer-keyid`
  (`e2b3d011…`). Своя CA в конец `ca.pem` → пакет ставится (бэкап
  `ca.pem.orig-omp`), но `security.ima` ставится нашим ключом → `EACCES`.
* `rpm -i --define '__transaction_validation %{nil}'` ставит без подписи, но
  без `xattr security.ima` → не запускается.
* Артефакты: `bin/` (validation.so, external_ima.so, load-certificates,
  update-revocation-list), `lk/lk_signoff.bin` (+zip).

## Приёмка

Свой бинарник/RPM, подписанный нами, запускается при `ima_appraise=enforce`
и `module.sig_enforce=1`, система при этом не жалуется (`/sys/kernel/security/ima/violations`
не растёт). Либо — документированное доказательство невозможности с точной
причиной и ссылками на ядро/ключи.
